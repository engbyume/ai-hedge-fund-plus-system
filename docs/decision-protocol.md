# Decision protocol

For each meaningful recommendation, create a compact record with these headings:

1. `Advice received`: what the system or another agent recommended.
2. `Evidence`: sources, dates, metrics, and data-quality state.
3. `Countercase`: what could make the thesis wrong.
4. `Operator decision`: bought, sold, held, rejected, deferred, or unavailable.
5. `Reason`: the operator's actual choice, including budget and platform constraints.
6. `System change`: whether the rule, prompt, data source, or code changed.
7. `Verification`: dry render, test, provider readback, or later outcome.
8. `Next review`: the date or condition that reopens the decision.

Do not rewrite the advice to make it match the outcome. A good record can say that the model was bullish, the operator could not buy because of a trade limit, and the result remains unknown.
